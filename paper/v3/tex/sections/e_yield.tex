\paragraph{The interleaved wave.}
Sixteen Vertex AI Spot jobs (one RTX PRO 6000 each, the replica image, the 25 demonstration games, 14 streams, one 7,200 s window) were launched on 2026-10-21 between 02:50 and 02:54 UTC: eight per arm, four per region per arm in us-central1 and us-east4, in A B B A order inside each region. The two builds differ in one line, the yield token count (8,192 against 2,048); both log requests. The design and decision rules are in a file dated 2026-10-21, written before the first job was submitted; its rules were amended at 02:55 while all 16 jobs were still pending and no run had started; the amendment changed how a result is split between decisions and tokens, and the null verdict is the same under both rule sets. Two jobs per arm never ran (three we cancelled after they sat pending in us-east4, one failed on a regional stockout), and each arm keeps the same regional split (five runs in us-central1, one in us-east4). % V3-W36 V3-W38
Four jobs never ran: three sat pending in us-east4 and were cancelled at 06:40 to free capacity for the adapter wave, and one failed on a regional stockout. No replacement ran, so the read uses six runs per arm (Table~\ref{tab:interleaved}). % V3-W36
The 8,192 arm scored 2.5 levels below the 2,048 arm (permutation $p$ 0.42; by region $-3.8$ in us-central1 and $+4.0$ in us-east4), 3.2 below at matched tokens, on 1.5\% more generated tokens and a third of the resume openers. At the six pairs' SD (8.25, 6 df) the 95\% interval on the difference is $-14.2$ to $+9.2$; at the SD of the eight same-day runs (5.95, 7 df) it is $-10.6$ to $+5.6$. The test therefore excludes the across-days $+12.5$ and any gain above about 9 levels, and does not exclude smaller gains. % V3-W36
Two candidate causes of the non-reproduction are drift between days and the extra tokens that seven of the nine across-days runs generated, worth about 5 of the 12.5 levels at the curve's elasticity; this test holds tokens equal and cannot apportion the two. % V3-W36 D8 D9

\paragraph{Mechanism and replay.}
Resume openers fell from 565, 634 and 572 per run at 2,048 to 185, 151 and 196 in the first three runs at 8,192, and stayed at 151 to 215 in all eight runs with transcripts, about 70\% fewer. Turn-start invocations, requests per turn and tokens per turn did not move. % D5
A resume costs 6.2K to 7.0K new prefill tokens on its first request, against 1.3K to 1.8K for a request inside an invocation. % D5
Re-cutting each recorded turn at the run's own threshold reproduces its resume count exactly: 546, 587 and 523 in the three 2,048 runs and 185 in the one 8,192 run with usage logs. These are counts over clean turns, 99\% of all turns. % D6
The replay is a deterministic rule checked against itself. Across thresholds it misses: the 2,048 traces re-cut at 8,192 give 135, 144 and 154 resumes, and the 8,192 run has 185, which is 20\% to 37\% more. The 8,192 trace re-cut at 2,048 gives 625, which is 6\% to 20\% more than the 523 to 587 observed. % D6



For each 2,048 run the replay also predicts the new prefill that the larger threshold would avoid: 1.82M, 2.20M and 1.90M tokens, against observed gaps to the first 8,192 run of 3.69M, 3.85M and 1.51M. The first two controls lack the reply-cache fix, so their gaps include another difference; the third is on the same code line. % D6 D7
The freed prefill is at most 2.3\% of the window by arithmetic and 0.6\% to 0.8\% by the server's prefill timers (Appendix~\ref{app:time}). % D7 F10

\paragraph{Discontinuity at the threshold.}
A request that lands just under or just over the threshold differs mainly in whether it was interrupted, because the reply length near the threshold is chance (Table~\ref{tab:rd}).
The next request acts more often after a resume at both thresholds. % D12
Removing resumes removes that nudge, so this does not explain the gain. Power is low, and the 8,192 rows rest on one run. % D12

\paragraph{Per-token clearance.}
Within game and level, the Mantel-Haenszel ratio of clearance per generated token is 1.073 for the nine against the 21 controls (run-cluster bootstrap CI 1.029 to 1.138, one-sided permutation $p=0.032$), 1.192 for the first two ($p=0.052$) and 1.071 for the later seven (CI 1.030 to 1.147, $p=0.082$). % D13
Scoring each run against the controls' rate per token instead gives 1.070 for the first two and 1.001 for the later seven ($p=0.17$). % D13
Censoring at the window end is informative, since the priority rule gives tokens to games that progress, so we read these ratios as indicative. They are strongest in the first two runs. % D13

\paragraph{What else differs between the arms.}
A cell-by-cell diff of the notebooks (26 cells each) shows that the first two's control and the first 8,192 run differ in the yield line and two fail-closed checks that raise only on the scored path. The first 8,192 run and its replicate differ in no cell, and the run with no token yield differs from its parent in the yield line only. % D1
The Kaggle same-code control also carries a strict thinking budget, which tied on its own promotion test. % B7
No same-platform, same-code 2,048 control at full window exists: the control of the first two ran on a cloud VM and the first 8,192 run on Kaggle, though 13 Kaggle controls average 111.3 and eight cloud controls 111.8. % D3

\paragraph{Choices made after seeing the data.}
We chose the control and treated sets (with eight and six as sensitivity rows), four further control subsets (Table~\ref{tab:yieldall}), nine token horizons (Table~\ref{tab:yieldtok}), the token values of Sec.~\ref{sec:yield} and levels rather than score as the outcome. The score gap is $+6.9$ points of mean game score (56.65 against 49.72). % D3 NEW:choices
